# Multi-Device Bluetooth Audio Manager
## Software Requirements Specification (SRS)

**Version:** 1.0
**Platforms:** Android and iOS
**Architecture:** Cross-platform UI with native audio-routing implementations

> Source baseline for all documents in this folder. Requirement IDs (DEV-, MED-, RTE-, VOIP-, CALL-, EXT-, CFG-, DIA-, NFR-) are referenced throughout the architecture, POC and test documents. See [13-requirements-traceability.md](13-requirements-traceability.md).

### 1. Product objective

Develop a mobile application that manages Bluetooth audio devices, provides configurable audio-routing preferences, supports multi-device playback where available, and routes app-owned communication audio independently of media where supported.

The application must clearly communicate platform and accessory limitations.

### 2. Functional requirements

#### 2.1 Device management

- **DEV-001:** Display available audio output devices exposed by the operating system.
- **DEV-002:** Display device name, type, connection status and capabilities where available.
- **DEV-003:** Use supported operating-system workflows for pairing and connecting devices.
- **DEV-004:** Monitor audio-route changes and device disconnections.
- **DEV-005:** Allow users to select, deselect and prioritize supported audio routes.
- **DEV-006:** Attempt reconnection only through permitted system mechanisms.
- **DEV-007:** Explain when a device is paired but unavailable as an audio output.
- **DEV-008:** Handle permissions, Bluetooth-disabled states and unsupported devices.

#### 2.2 Multi-device media playback

- **MED-001:** Play supported media through a selected audio output.
- **MED-002:** Support simultaneous playback to multiple outputs when the platform, device and accessory combination permits it.
- **MED-003:** Provide play, pause, seek and playback status controls for app-owned media.
- **MED-004:** Display the actual active output routes where observable.
- **MED-005:** Handle output disconnections without crashing.
- **MED-006:** Apply a configurable fallback policy after route failure.
- **MED-007:** Measure synchronization differences during supported multi-output tests.
- **MED-008:** Support independent per-device volume only where the relevant controls are exposed.

#### 2.3 Music and communication routing

- **RTE-001:** Let users configure a preferred media output.
- **RTE-002:** Let users configure a preferred communication output.
- **RTE-003:** Request separate media and communication routes where supported.
- **RTE-004:** Confirm route changes through observable system state.
- **RTE-005:** Display an error when a requested route is rejected or unavailable.
- **RTE-006:** Restore previous preferences after a communication session where possible.
- **RTE-007:** Handle incoming and outgoing call interruptions and changes in audio focus.
- **RTE-008:** Never represent a preference as a successful route until the route is confirmed.

#### 2.4 Voice over IP

- **VOIP-001:** Support audio input and output for calls made within the application, if the VoIP feature is included.
- **VOIP-002:** Request supported communication-device routing using native APIs.
- **VOIP-003:** Handle microphone permissions, mute, call termination and interruptions.
- **VOIP-004:** Support switching communication outputs when permitted.
- **VOIP-005:** Release communication routing resources when a call ends.
- **VOIP-006:** Keep call audio separate from media audio only where the OS and hardware permit it.

#### 2.5 Cellular calls

- **CALL-001:** Display supported call-routing information when the OS exposes it.
- **CALL-002:** Do not assume that a normal third-party app can control the system dialer's audio destination.
- **CALL-003:** Provide instructions for supported system-level route selection when direct control is unavailable.
- **CALL-004:** Do not record cellular calls or capture call audio as part of the baseline feature set.
- **CALL-005:** Treat direct cellular-call routing as a separately validated platform-specific feature.

#### 2.6 Third-party media applications

- **EXT-001:** Do not promise direct routing control over Spotify, YouTube or arbitrary third-party audio.
- **EXT-002:** Allow users to configure supported system-level audio preferences where available.
- **EXT-003:** Explain that selecting a preferred route in this app may not redirect audio generated by another app.
- **EXT-004:** Evaluate OS-provided audio-sharing capabilities separately from app-controlled routing.
- **EXT-005:** Do not capture, retransmit or process third-party audio without a lawful, platform-supported mechanism and appropriate authorization.

#### 2.7 Profiles and automation

- **CFG-001:** Create, edit, rename and delete routing profiles.
- **CFG-002:** Save preferred media and communication devices.
- **CFG-003:** Provide Music, Calls, Multi-Device and Custom profiles.
- **CFG-004:** Define fallback behavior when a preferred device disconnects.
- **CFG-005:** Apply profiles manually.
- **CFG-006:** Support connection-triggered automation where background and platform policies allow it.
- **CFG-007:** Preserve preferences across application restarts.
- **CFG-008:** Allow manual overrides of automated preferences.

#### 2.8 Diagnostics and privacy

- **DIA-001:** Show requested, available and active routes separately.
- **DIA-002:** Provide a compatibility test for the current phone and connected accessories.
- **DIA-003:** Record technical error codes without unnecessarily recording personal audio information.
- **DIA-004:** Explain required permissions and their purpose.
- **DIA-005:** Request microphone access only for relevant features.
- **DIA-006:** Avoid collecting call content or unrelated third-party audio.
- **DIA-007:** Provide user-readable troubleshooting guidance.

### 3. Non-functional requirements

- **NFR-001:** No crashes during repeated device connections, disconnections or route changes.
- **NFR-002:** Route status must reflect observable system state.
- **NFR-003:** Minimize playback interruptions and route-switching latency.
- **NFR-004:** Minimize battery consumption and unnecessary background activity.
- **NFR-005:** Store profiles locally for offline use.
- **NFR-006:** Protect locally stored settings and diagnostic information.
- **NFR-007:** Support accessibility, screen-reader labels and clear error messages.
- **NFR-008:** Define supported OS versions after feasibility testing.
- **NFR-009:** Test against a documented device and accessory compatibility matrix.
- **NFR-010:** Do not guarantee audio synchronization or multi-device routing outside validated configurations.

### 4. Platform-specific technical requirements

**Android**
- Kotlin and Jetpack Compose for the native application layer.
- Android Bluetooth APIs for supported discovery and connection workflows.
- AudioManager and AudioDeviceInfo for observable routing and device information.
- setCommunicationDevice() for supported app communication sessions.
- Android Telecom APIs for integration with the app's own VoIP calls where appropriate.
- AndroidX Media3 for app-owned media playback.
- Room or DataStore for local configuration.

Privileged combined-audio-routing APIs must not be treated as available to ordinary third-party apps.

**iOS**
- Swift and SwiftUI for the native application layer.
- AVAudioSession for app audio-session configuration and route-change handling.
- AVAudioSession route information and supported routing controls for output selection.
- AVAudioSession multiRoute only for supported combinations, not as a promise of arbitrary multi-Bluetooth output.
- A suitable audio engine and VoIP implementation for app-owned audio.
- Local persistence for routing profiles.

The app must respect iOS audio-session arbitration and cannot assume control over other applications' audio or cellular-call routing.

### 5. Acceptance criteria

1. The app displays available supported audio routes.
2. Users can create, edit and restore routing profiles.
3. App-owned media plays through a selected supported output.
4. VoIP communication uses the selected supported route when the request succeeds.
5. Multi-output playback passes tests on each specifically declared compatible configuration.
6. Unsupported route combinations generate actionable errors.
7. Disconnecting an output does not crash the application.
8. Requested routes and actual active routes are distinguishable.
9. Cellular-call and third-party-audio limitations are disclosed.
10. Permission, privacy, battery and background-operation tests pass.

### 6. Out of scope for version 1.0

- Universal redirection of third-party app audio.
- Universal control of cellular-call routing.
- Bypassing OS restrictions or acquiring undocumented privileged APIs.
- Guaranteed simultaneous output across arbitrary Bluetooth accessories.
- Guaranteed zero-latency or perfectly synchronized independent Bluetooth connections.
- Cellular-call recording.
- Mandatory cloud backend, user accounts or subscriptions.

### 7. Required deliverables

1. Platform feasibility report.
2. Native audio-routing proof of concept.
3. Cross-platform UI prototype.
4. Android and iOS implementations.
5. Automated and physical-device test suites.
6. Compatibility matrix and documented limitations.
7. Release builds, source code and deployment documentation.
